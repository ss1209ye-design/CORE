# UI/UX와 KRDS 참고 안내

UI는 버튼·입력창·메뉴 등 사용자가 접하는 화면 요소이고, UX는 목적을 달성하는 전체 사용 경험입니다. 화면을 예쁘게 만드는 것과 함께 사용자가 다음 행동을 이해하고 실수에서 회복할 수 있는지 계획하세요.

이 문서는 비개발자와 에이전트가 화면을 계획·검증할 때 쓰는 안내입니다. 문서 추가만으로 현재 화면에 KRDS 디자인이 적용되거나 접근성 검증이 완료되지는 않습니다. 기본 실행은 [설치 안내](SETUP.md)를 참고하세요.

## KRDS는 무엇인가요?

KRDS(Korea Design System)는 디지털 정부서비스의 일관된 화면과 사용 경험을 위한 원칙·스타일·컴포넌트·패턴 등을 제공합니다. 색상·글꼴·간격은 스타일, 버튼·입력창은 컴포넌트, 로그인·신청 등 목적을 이루는 흐름은 패턴 관점에서 참고할 수 있습니다. [KRDS 공식 소개](https://www.krds.go.kr/html/site/utility/utility_01.html)

아래 확인표는 이 보일러플레이트에서 활용할 요약·권고이며 공식 가이드라인 전체나 인증 기준을 대체하지 않습니다. 특정 수치·구현 조건이 필요하면 해당 요소의 최신 공식 안내와 프로젝트에서 정한 적용 버전을 확인하세요.

## 적용 범위부터 정하기

| 프로젝트 상황                    | 선택·확인할 내용                                                                   |
| -------------------------------- | ---------------------------------------------------------------------------------- |
| 일반 서비스·MVP                  | 기존 디자인을 유지하면서 필요한 가독성·일관성·접근성 원칙과 패턴을 선택적으로 참고 |
| 공공 프로젝트                    | 발주·기관 요구사항과 공식 적용 기준을 확인하고 대상 화면·항목·검증 범위를 합의     |
| 이미 디자인 기준이 있는 프로젝트 | 기존 기준과 비교해 도입 이점·충돌·영향을 설명하고 필요한 항목만 변경               |
| 화면과 무관한 DB·서버 작업       | UI 변경이 없으면 상세 화면 설계 생략 가능                                          |

디지털 정부서비스 UI/UX 가이드라인은 공공 서비스의 설계·구현 기준을 설명합니다. 일반 민간 서비스에 모든 항목이 의무 적용된다고 단정하지 않으며 공공 프로젝트의 세부 요구도 문서만으로 추측하지 않습니다. [공식 가이드라인 소개](https://www.krds.go.kr/html/site/utility/utility_07.html)

정부 공식 배너·기관 이름·로고 등은 일반 서비스에 그대로 넣지 않습니다. 파일·폰트·아이콘·코드를 가져온다면 해당 리소스의 이용·저작권 조건도 확인하세요. KRDS 참고와 공식 정부서비스를 나타내는 표현의 사용은 별개입니다.

## 화면 개발 전에 정할 것

1. 비회원·일반 사용자·관리자 등 실제 사용자와 핵심 목표를 정합니다. 관리자 화면은 필요한 서비스에서만 계획합니다.
2. 진입 → 조회·입력 → 확인·제출 → 결과의 주요 흐름을 정합니다. 사용자가 현재 위치와 다음 행동을 이해할 수 있어야 합니다.
3. 화면·메뉴·버튼·입력 항목을 정하고 비슷한 기능의 용어와 동작을 맞춥니다. 공통 화면과 역할별 기능을 구분합니다.
4. 필요한 정상·로딩·성공·오류·빈 상태·접근 제한과 입력 보존·재시도·중요 작업 확인을 계획합니다.
5. KRDS에서 참고할 관련 스타일·컴포넌트·패턴을 골라 공식 URL·버전 또는 확인 기준과 적용·제외 이유를 기록합니다. 모든 컴포넌트를 도입할 필요는 없습니다.

역할별 메뉴 구분은 서버 권한 검사를 대신하지 않습니다. [보안 안내](SECURITY.md), [유효성 검사](VALIDATION.md)를 함께 참고하세요. 폰트와 공통 UI 재사용은 [폰트 안내](FONTS.md)와 [아토믹 디자인 안내](CODEX_GUIDE.md#화면-재사용과-아토믹-디자인-선택-사항)를 활용합니다.

## 화면·사용성 확인표

| 항목             | 사용자 관점의 질문                                                                                |
| ---------------- | ------------------------------------------------------------------------------------------------- |
| 정보와 흐름      | 이 화면의 목적·현재 위치·다음 행동이 명확한가? 불필요한 반복 입력이 없는가?                       |
| 일관성           | 메뉴·버튼·용어·색상·간격이 같은 의미에 일관되게 사용되는가?                                       |
| 입력             | 라벨·필수 여부·입력 예시가 있고 오류 위치와 수정 방법을 알 수 있는가?                             |
| 상태 안내        | 처리 중·성공·실패·결과 없음·접근 제한을 구분하고 다음 행동을 제공하는가?                          |
| 실수와 복구      | 중복 제출·입력 손실을 막고, 중요한 삭제·취소에 영향에 맞는 확인이나 복구가 있는가?                |
| 키보드와 포커스  | 마우스 없이 주요 작업을 완료하고 현재 포커스를 볼 수 있는가? 모달 종료 후 적절히 돌아오는가?      |
| 의미와 대체 정보 | 제목·버튼·링크·입력창을 적절한 HTML로 표현하고 이미지에 필요한 대체 설명이 있는가?                |
| 가독성과 대비    | 글자가 읽기 쉽고 색만으로 오류·상태를 구분하지 않는가? 선택한 대비 기준을 확인했는가?             |
| 반응형과 확대    | 모바일·화면 확대에서 내용과 조작 요소가 겹치거나 잘리지 않는가? 필요한 표 스크롤이 사용 가능한가? |

이 표는 자체 검토용입니다. 실제 치수·색 대비·키보드 동작 등은 선택한 공식 항목과 적용 기준에 맞춰 확인하세요. 모든 작업에 확인창을 붙이거나 모든 상태를 억지로 만들 필요는 없습니다. 위험과 사용 흐름에 필요한 항목을 선택합니다.

## 현재 기술에 적용하기

Next.js·Tailwind와 기존 컴포넌트로 선택한 기준을 구현할 수 있습니다. 스타일 전체를 복사하거나 별도 UI 라이브러리를 의무적으로 설치하는 방식은 아닙니다. 공식 HTML 예제의 모양뿐 아니라 의미·키보드·포커스·상태 안내를 현재 React 구성에 맞게 검토해야 합니다.

기존 디자인 변경, 리소스 다운로드, 패키지 설치는 필요한 파일·영향을 확인한 뒤 승인 범위에서 진행합니다. 컴포넌트의 위치나 Server·Client 경계를 임의로 일괄 변경하지 않습니다. 단순 수정에는 관련 기준만 적용하며 이미 정한 같은 범위는 반복해서 묻지 않습니다.

## 무엇을 검증했는지 구분하기

코드 검토·타입·린트·빌드·HTTP 응답 확인은 실제 브라우저 사용성 검증과 다릅니다. 핵심 흐름, 필요한 오류·빈 상태, 모바일, 키보드·포커스, 확대·대비를 실제 확인하고 환경·방법·결과·남은 작업을 남기세요. 화면을 보지 못했다면 시각 검증 완료로 기록하지 않습니다.

일부 기준을 참고한 화면을 KRDS 전체 준수 또는 웹 접근성 인증 완료로 표현하지 않습니다. 공공 프로젝트의 별도 평가·인증 요구는 해당 요구에 맞는 검증이 필요합니다. 관련 결정과 예외·근거는 [계획 양식](../plans/README.md)에 기록할 수 있습니다.

## 에이전트에 요청하기

```text
[서비스·화면]의 사용자 역할과 핵심 목표를 정리하고 docs/UI_UX.md 기준으로 계획해 주세요.
기존 디자인을 먼저 확인하고 KRDS의 관련 원칙·컴포넌트·패턴을 제안해 주세요.
일반 서비스의 선택적 참고인지 공공 프로젝트의 요구 기준인지 구분하고,
공식 참고 URL·적용 항목·예외 사유와 실제 브라우저 검증 계획을 보여 주세요.
정부 공식 배너·기관 식별 요소를 임의로 넣지 말고,
아직 화면 변경·리소스 다운로드·패키지 설치는 진행하지 마세요.
```

에이전트의 상세 기준은 [프론트엔드 지침](../.agent/frontend.md#uiux와-krds-참고-기준), 공식 자료 탐색은 [KRDS](https://www.krds.go.kr/)를 참고하세요.

## 꿀잡 로컬 화면 사용

- 상단 로고·피기·지정된 말풍선 PNG 원본을 보존하고 서비스 안내에서 말풍선 이미지를 표시합니다. 불투명한 메인 로고 원본의 배경은 임의로 제거하지 않습니다.
- 랜딩의 서비스 안내·로그인 버튼은 왼쪽 상단에서 같은 스타일로 표시합니다. 로그인 후에는 포트폴리오·자기소개서·면접 연습 메뉴를 직접 누르며, 펼침 화살표와 메뉴 폴더는 없습니다. 현재 메뉴를 구분하고 마이페이지는 둥근 버튼으로 유지합니다.
- 서비스 안내는 6개 주제·17개 문단을 가운데 정렬해 표시합니다. 설명 단계는 이전·다음 화살표로만 이동하며 실제 스크롤은 유지합니다. 문장 바로 보기와 스크롤 안내 문구는 제거하고 마지막 페이지는 시작하기/닫기로 종료합니다. 둥근 시스템 글꼴을 우선하되 설치 여부에 따라 기존 글꼴로 대체됩니다.
- Skip은 가입 직후 자동 안내에서만 표시합니다. 수동 서비스 안내에는 Skip이 없으며 닫아도 기존 화면·미저장 입력을 유지합니다. 완료 상태는 계정에 보관합니다.
- 캘린더는 연도·월 텍스트를 눌러 선택합니다. 좌우 월 이동 화살표는 없습니다. 홈의 `+`로 공고를 등록합니다. 작게 표시한 마이페이지 버튼은 기존 화면으로 이동하며 로그아웃은 마이페이지 최하단에 있습니다. 로그인 전 기록 가져오기 UI는 제거했지만 기존 저장값은 삭제하지 않습니다.
- 공고는 링크 저장과 직접 입력·원문 붙여넣기만 지원합니다. 사진 업로드·로컬 OCR·사진 AI 분석·URL 본문 가져오기 UI는 사용하지 않습니다. 기존 공고의 링크·원문·조건·서류·확정 일정은 보존됩니다.
- 링크만으로도 임시 제목과 정보 미확인 상태로 저장할 수 있습니다. 병원명·모집 직무·지원 기간·조건·서류는 직접 입력하며 필수 날짜는 없습니다. 날짜 없는 공고도 목록에서 수정하고, 직접 확인한 시작일과 마감일만 피기캘린더에 반영합니다.
- 공고 사진·URL 분석 전용 컴포넌트·API·처리 코드와 의존성을 제거했습니다. 이전 분석 주소는 404이며, 링크를 저장해도 서버가 원문을 수집하지 않습니다. 기존 공고 데이터와 공통 Gemini 코드는 유지합니다.
- 포트폴리오는 제목·유형·기간·실제 수행 수준·내용을 입력하거나 UTF-8 `.txt`·`.md` 자료(128KB, 12,000자 이하)를 브라우저에서 읽습니다. AI 추출은 역할·행동·역량·배운 점을 근거로 3~5개 키워드를 만들고 원문 근거를 보여 줍니다. 태그는 수정·삭제·직접 추가 후 경험과 함께 저장합니다. 제공한 5개 예시는 시연용 가상 자료로 표시하며 재접속 시 자동 제거하지 않습니다. 근거가 부족하면 키워드를 억지로 채우지 않고 보완 질문을 표시하며 기존 태그를 유지합니다.
- 자기소개서는 문항·선택한 경험과 저장된 키워드를 Google Gemini API에 보내 초안을 만듭니다. 공고는 선택 사항으로, 공고가 없거나 연결하지 않으면 경험을 바탕으로 생성·저장합니다. 공고를 선택한 경우에만 해당 공고를 함께 전달합니다. 사용한 경험·인용 근거·추가 확인 질문과 생성 당시 자료를 보관합니다. 관찰·보조를 독립 수행으로 바꾸거나 없는 성과를 만들지 않도록 지시하고 출처·인용·일부 수치 표현을 검증하지만 의미상 정확성을 완전히 보장하지는 않습니다. 수정본과 제출본은 자동으로 덮어쓰지 않습니다. 희망 직무를 선택 입력할 수 있으며 공고가 없으면 일반 지원용 초안으로 표시합니다.
- 면접 연습은 자소서 또는 선택한 포트폴리오로 시작하고 공고는 선택 사항입니다. 사용자가 연습 제목을 입력하며 병원명은 선택 입력입니다. 제목 수정과 전체·병원 미지정·병원별 필터를 제공하고 질문 근거·답변·보완점·복기를 저장합니다. 이전 기록의 제목·출처는 유지하며 병원명 없는 기록도 읽습니다.
- 키워드 추출·자기소개서 초안·면접 질문·꼬리 질문·답변 피드백은 고정 모델 `gemini-3.6-flash`를 사용합니다. 과거 AI 제공자가 만든 기존 기록과 생성 당시 제공자 표시는 그대로 보존하며, 새 Gemini 결과로 덮어쓰지 않습니다.
- AI 실패·취소·설정 누락 시 고정 결과로 대체하지 않습니다. 입력과 이미 저장한 답변을 유지합니다. 저장 공간 부족·다른 창 충돌 시 성공으로 표시하지 않고 현재 입력을 보존합니다. 중요한 자료는 별도로 복사해 보관하세요.
- 로딩 돼지는 지면에 수직인 Y축으로 정면 → 오른쪽 → 뒤 → 왼쪽 → 정면 회전합니다. 안내 돼지는 첫 화면에서만 서서 손을 흔들고 나머지 화면에서는 정지합니다. 움직임 줄이기 설정에서는 정적인 자세를 사용하며 처리를 애니메이션 종료까지 지연하지 않습니다.
- 개발·빌드·설치 과정에서 OCR 런타임을 준비하지 않습니다. 기존 사용자 첨부 자료는 삭제하지 않습니다.
- 준비 기록은 사용자 ID별 현재 브라우저에만 저장됩니다. 계정만 로컬 서버 DB에 보관하며 기록의 서버 동기화는 제공하지 않습니다.

### Google Gemini 연결 설정

1. [Google AI Studio API 키](https://aistudio.google.com/apikey)에서 사용할 프로젝트를 선택하거나 새로 만듭니다. **결제가 연결되지 않은 프로젝트만** 사용하세요. 앱은 API 키만으로 프로젝트의 결제 연결 상태를 확인할 수 없습니다.
2. [AI Studio 프로젝트 목록](https://aistudio.google.com/projects)에서 프로젝트가 Free인지, 결제가 연결되지 않았는지 확인하고 [사용 한도](https://aistudio.google.com/rate-limit)를 확인합니다. [모델 가격표](https://ai.google.dev/gemini-api/docs/pricing#gemini-3.6-flash)에는 `gemini-3.6-flash`의 Free 티어 입력·출력이 표시되지만, 이를 모든 프로젝트·상황의 비용 0원 보장으로 해석하지 마세요. 한도는 프로젝트별·시점별로 달라집니다. Free에서 유료로 전환하려면 활성 결제 계정 연결이 필요합니다. [모델 안내](https://ai.google.dev/gemini-api/docs/models/gemini-3.6-flash)는 텍스트·이미지 입력과 구조화 출력을 설명합니다.
3. AI Studio에서 Gemini API로 제한한 키를 발급합니다. 키를 대화·코드·공개 저장소에 붙여넣거나 `NEXT_PUBLIC_` 변수로 만들지 마세요. 모델은 `gemini-3.6-flash`로 고정되어 있어 별도의 모델 선택·재정의 변수는 필요하지 않습니다.
4. 기존 `.env.local`의 다른 값을 보존하고 `GEMINI_API_KEY`에 발급 키를 추가합니다. 프로젝트의 Free 상태와 결제 미연결을 직접 확인한 뒤에만 `GEMINI_FREE_TIER_CONFIRMED=true`를 설정하세요. 확인 전에는 `false`로 둡니다. 이 확인 플래그는 앱에 결제 상태를 알려 주지 않으며 사용자의 확인을 기록하는 설정입니다.
5. 현재 로컬 서버 터미널에서 `Ctrl+C`로 중지합니다. 소스가 바뀌었다면 먼저 `npm run build`를 실행하고, 빌드된 서버는 `npm run start -- --hostname 127.0.0.1`로 시작합니다. 개발 서버는 `npm run dev -- --hostname 127.0.0.1`로 시작합니다.
6. 화면의 AI 설정을 다시 확인하거나 새로고침합니다. 표시되는 설정 상태는 키와 확인 플래그의 설정 여부이며 실제 API 연결, 결제 연결 여부, 남은 쿼터까지 검증한 결과가 아닙니다.
7. 키워드·초안·면접·피드백 AI 기능만 사용자가 실행한 요청의 선택 자료를 Google에 전송합니다. 사용자가 연결한 공고의 저장된 텍스트는 자소서·면접의 참고 자료가 될 수 있지만, 공고 사진이나 URL 본문을 수집·분석하지 않습니다. Gemini 요청은 단발 `generateContent` 방식, 서버 60초 제한, 자동 재시도·유료 대체·검색 도구 없이 실행됩니다. Free 티어 입력과 응답은 Google 제품 개선에 사용될 수 있으므로 **시연에는 허구의 비민감 자료만 사용하세요**. 대화 저장 API를 사용하지 않아도 Google의 데이터 이용 정책은 적용됩니다.
8. 한도 초과 시 결제를 연결하거나 유료 티어로 전환하지 마세요. 프로젝트 한도와 상태를 다시 확인하고 한도가 회복될 때까지 기다리거나 수동 입력을 사용하세요. 실패해도 기존 입력과 저장 기록은 유지됩니다. API 쿼터는 프로젝트별로 달라 고정 수치를 안내할 수 없습니다.
9. 로컬 실제 검증에서 키워드 3개 추출은 브라우저·서버를 통해 약 2.3초에 성공했고, 면접은 서버 생성 함수에서 질문 5개와 근거 검증을 통과했습니다. 자소서는 경험 ID 불일치로 거절되어 출력 스키마를 보완했으며, 수정 후 실제 응답은 재검증 전입니다. 모의 화면 검사와 실제 제공업체 응답을 구분합니다.

공고 분석 기능은 제거했습니다. 서버 DB 저장·기기 간 동기화·Vercel 배포는 아직 구현·검증되지 않았습니다. 기존 계정은 SQLite에, 준비 기록은 브라우저에 남아 있습니다.

### 최근 로컬 화면 측정

390px·브라우저 캐시 비활성화·localhost에서 첫 콘텐츠 표시(FCP)는 변경 전 128ms, 변경 후 124ms였습니다. 단회 측정이므로 유의미한 속도 향상이나 실제 모바일 통신망 성능을 입증하지 않습니다. 초기 글꼴 전송량은 약 2.06MB, 피기 모델은 약 569KB였으며 주요 버튼은 먼저 표시됩니다. 홈에서 불필요한 AI 설정 조회를 없애 실제 `/api/ai` 요청 0건을 확인했습니다. 320·390·1280px의 직접 메뉴와 가이드 가로 잘림을 검사했습니다.

### 피기캘린더의 지원 기간

- 기존 공고의 `applicationStart`와 `deadline`을 그대로 사용합니다. 기존 `dateConfirmed`는 마감일 확인 의미를 유지하고, 시작일은 별도 `startDateConfirmed`로 확인합니다. 과거 시작일을 자동으로 확인 처리하지 않습니다.
- 확인한 두 날짜가 있으면 시작일부터 마감일까지 포함하는 막대를 표시합니다. 한 날짜만 확인되면 그 날짜의 일정만 표시하고, 둘 다 없거나 미확인인 공고는 목록에 보관합니다.
- 막대와 일정 목록에서 공고 상세로 이동합니다. 주·월 경계에서는 기간을 나누어 이어 표시하고, 겹치는 공고는 별도 줄에 놓습니다. 모바일에서도 전체 기간을 일정 목록으로 확인할 수 있습니다.
- 날짜를 수정하면 해당 날짜의 확인 체크가 해제됩니다. 역전된 기간은 마감일 입력란에서 안내하고 저장을 막습니다. 일정은 공고 데이터에서 계산하므로 별도 중복 일정이나 사용자 기록 재설정 없이 수정·삭제 결과를 반영합니다.

- 날짜별 목록은 선택한 날을 포함하는 모든 확인된 기간을 표시하고, 공고 제목 아래에 전체 지원 기간을 안내합니다. 연도를 넘으면 양쪽 연도도 표시하며, 한 날짜만 확인된 경우 시작일 또는 마감일만 안내합니다.
- 서비스 안내에서 페이지를 바꾸면 기존 피기 모델의 팔과 몸을 이용한 약 0.92초 동작을 재생합니다. 빠른 전환은 현재 자세에서 최신 동작으로 대체하며 모델을 다시 불러오지 않습니다. 움직임 줄이기 설정에서는 정적인 자세를 유지합니다.
